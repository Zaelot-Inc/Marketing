01 What that quote was paying for

The old way

Here's how a migration has worked for the last 25 years:

  1. A project owner lists every page in a spreadsheet.
  2. Content editors or junior developers copy each page into the new CMS, fix the links, and re-upload the images.
  3. Developers rebuild every page template by hand so the new site can show the content.
  4. QA testers check a sample of the work, because checking every page would take too long.

The old way, added up

5,000+ hours

Four people for eight months. That's your $500K quote.

The bigger the site, the bigger the bill. Manual processes almost guarantee there are bugs and pages that need to be fixed post-launch. Manual migration was a messy, stressful process.

03 The new way

Migrations aren't done page by page anymore

AI agents now do the page-by-page work. People make the decisions.

  1. 1

    Every page gets looked at first.

    An agent sorts every page by type, reading the pages and the code together when the structure was never written down. Pages that don't fit get flagged with a reason. Each extra source CMS is a small added step, not a new project.

  2. 2

    The content model gets written down, and people sign off.

    Your team and the builders agree on the content model. Agents suggest where each piece of old content goes; people approve or change it. Nothing gets deleted without a person signing off.

  3. 3

    The new site gets built from the plan.

    Agents build each template and its building blocks from the same content model, so content and site fit from day one. Builders review code instead of writing every template by hand.

  4. 4

    Every page gets checked, not a sample.

    Machines compare old and new: every field, link, image, and redirect, in every language, plus how each page looks. Anything that doesn't match goes to a person before launch day.

  5. 5

    Launch gets rehearsed until it's boring.

    Because the process runs automatically, the team can do full practice runs again and again. On launch day, the old site stays ready as a backup.

This works on the two migrations we see most often: several CMSs behind one website that need to become one, and a vibe-coded or no-code site (Builder, Framer, Lovable, Bolt, v0) that a growing team has outgrown.
